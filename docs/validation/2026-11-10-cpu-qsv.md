The file was verified to be a regular file and read before editing. Backups of
its original Compose file, Jellyfin `encoding.xml`, and container inspection
were saved privately in CT 105 at:


The directory is mode `0700`; saved encoding and inspection files are mode
`0600`. Do not publish their contents: inspection may include private settings.
Compose validation passed before recreating only Jellyfin with
`docker compose up -d --no-deps --pull never jellyfin`. No image was pulled or
upgraded. Existing volumes, mount guard, read-only media binding, entrypoint,
and other services were retained. The live container uses the existing
`jellyfin/jellyfin:10.11.8` image; the repository retains its existing digest pin.

After successful HEVC tests, the application codec list was extended from
`h264,vc1` to `h264,vc1,hevc`, with Jellyfin stopped during the file edit. The
existing HEVC Main10 decode flag remains enabled. Quick Sync and hardware
encoding remain selected. After the successful HDR test below, OpenCL tone mapping
was enabled with Jellyfin stopped during the edit; the prior encoding settings
were saved privately as `encoding.pre-tonemapping.xml` in the rollback directory.
Intel VPP tone mapping, Intel low-power encoders, HEVC output, and AV1 output
remain disabled. These application setting changes are persisted
in the existing configuration volume, not represented by Compose environment
variables. Jellyfin returned to `running healthy` after restart.

To roll back, stop Jellyfin, restore the saved Compose and `encoding.xml` to
their original locations, and recreate only Jellyfin without pulling images.
The original settings selected QSV despite the missing device; to explicitly
fall back to software, select hardware acceleration `None` in Jellyfin. Keep
all existing volumes and media mount protection.

### Follow-up load and fallback checks

Two real library segments (H.264 SDR and HEVC 10-bit BT.709) were transcoded
concurrently to 1280-pixel-wide H.264 at 2 Mbps with input limited to real time.
Both completed 60 seconds / 1,439 frames with exit 0, approximately 24 fps and
1× playback speed. During this bounded test, sampled maximum sensor temperatures
ranged from 38 to 48°C; all exposed package/core throttle counters remained zero.
This demonstrates two short real-time video-only pipelines, not maximum
concurrency or a long-duration household streaming soak.

A matched 12-second H.264 segment produced 288 frames at 14.6× with QSV versus
7.17× / 173 fps using `libx264`, preset `veryfast`, and two software threads.
Both exited 0. Encoder quality settings differ, so this is a functional fallback
and throughput comparison rather than an equal-quality encoder benchmark.

An initial isolated HDR OpenCL experiment failed with exit 218 before producing
frames: its reverse hardware map through VA-API returned `Function not implemented`.
A subsequent direct OpenCL→QSV map succeeded on the real HEVC 10-bit PQ sample A.
The chain used VA-API decode/scale, `hwmap=derive_device=opencl:mode=read`,
`tonemap_opencl` with BT.2390, and
`hwmap=derive_device=qsv:mode=write:reverse=1:extra_hw_frames=16`, followed by
`format=qsv` and `h264_qsv` encoding at 2 Mbps. With `peak=100`, the eight-second
segment produced 192 frames, exit 0, about 74 fps / 3.03×. A follow-up using the
saved default `peak=0` also produced 192 frames, exit 0, about 112 fps / 4.58×.
Both outputs were H.264 1280×692 yuv420p with BT.709 matrix, transfer, and
primaries. Disposable output clips were removed. These results establish the
functional command-line HDR→SDR path and output metadata; visual quality and
actual client HDR playback remain unverified. OpenCL tone mapping is now enabled
in the saved application settings, and Jellyfin returned to `running healthy`.

After reboot, an eight-second H.264 library segment with a disposable SRT test
subtitle passed QSV decode/scale → frame download → libass subtitle rendering
→ frame upload → QSV H.264 encode. It produced 192 frames, exit 0, at 11.5×.
The test subtitle was removed afterward. This verifies the command-line burn-in
pipeline, including its expected software text-rendering stage. The later client
PGS selection and visual check are recorded below.
